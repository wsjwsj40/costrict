# DiCode Codex MVP

Independent VS Code extension using the unmodified `codex app-server` as its local agent. The existing DiCode login and model list endpoints supply credentials and model IDs. The selected model runs through the standalone `dicode-codex-bridge` Responses endpoint.

The extension automatically downloads the platform-specific unmodified Codex CLI from the DiCode portal on first activation. The installer verifies the archive, waits for extraction handles to close, and can finish by copying the package if Windows blocks the final directory rename. The JSON-RPC handshake and ephemeral thread creation were checked against `codex-cli 0.164.0`. Set `dicodeCodex.serverUrl` to the DiCode APISIX entry. Set `dicodeCodex.codexPath` only to override automatic installation with an existing executable. The extension reads the CLI's bundled model catalog with `codex debug models --bundled` and uses its native instruction template for DiCode model entries. An exact model ID match uses that model's template; other IDs use the bundled model with the lowest priority number. The generated catalog retains `apply_patch_tool_type: freeform`, because Codex does not register its dedicated patch tool for unknown model IDs by default. The extension adds only DiCode identity through `developer_instructions`; it does not replace the CLI's base instructions. The upstream Responses endpoint must support custom freeform tools for the patch tool to work.

The sidebar now renders app-server Thread, Turn and Item events. It includes streaming Markdown with syntax highlighted code blocks, command output, file changes with inline and native editor Diff, plan updates, tool activity and approval requests. The recent-thread menu keeps up to 20 sessions, with the latest 20 turns cached per session in VS Code global state; long command outputs are truncated in that cache. Run `npm ci && npm run build && npm test`, then `npx vsce package --no-dependencies`, or launch VS Code's Extension Development Host with this folder as the extension path. The bundled `media/bundle.js` is included in the VSIX, so the webview works without a CDN.

Version 0.2.15 groups each turn's reasoning summaries, commentary, commands, tools, plan and file diffs in a single process section. During a run, a pinned plan card shows the current step and completed count; it expands to the full list. On completion, the process section folds to a compact elapsed-time label such as `用时1分26秒`; the final answer stays visible below it. Command and tool activity use muted colors. Turn timestamps are persisted so elapsed time survives history reload; older turns without timestamps show a neutral `过程` label. Active approval and user-input prompts remain visible outside the folded process.

Version 0.2.16 moves the live plan card directly above the composer. Its collapsed row retains the current step and completed count; expanding it shows the full list. The plan is no longer repeated in the turn's process details.

Version 0.2.17 hides reasoning events from the conversation, including restored history. A subtle wave of dots marks the running plan step in both the collapsed and expanded plan card; reduced-motion preferences disable the animation.

Version 0.2.18 replaces the running plan step's dot animation with a moving highlight across the step text, inspired by the Codex CLI status shimmer. The symbol and count stay still, and reduced-motion preferences show static text.

Version 0.2.19 refreshes the sidebar to match the Codex conversation layout. Running commands and file edits shimmer; completed commands fold into an "已运行命令" group. A live change card opens VS Code Diff, and completed turns show a file list with line counts. Approval requests use a compact terminal-style card. VS Code Diff also supports newly created and deleted files.

Version 0.2.20 keeps the permission and model menus inside narrow sidebar bounds, adjusting their position and scroll height when space is limited. It also aligns the disclosure arrows for command groups, elapsed time, permission mode, and model selection.

Version 0.2.21 groups commands, searches, and file edits under Chinese activity summaries, with a compact terminal icon for commands and one row per edited file. Single activities show directly. Command headings use one-line previews while expanded details retain the full command. The model picker is narrower, the back-to-bottom button is centered and icon-only, and the sidebar's right edge is clearer.

Version 0.2.22 uses the same terminal icon for command rows and group headings, lets command summaries truncate to the available width, and groups consecutive commands and edits across in-progress and invisible events. Visible commentary separates groups. The model list sizes to its content within the sidebar.

Version 0.2.23 asks Codex to use its file editing tool for text changes so app-server can emit file change events. Local `rg` searches remain command execution events; the sidebar labels them as code searches even when Codex omits command action metadata. The instructions distinguish local searches from web search events.

Version 0.2.25 returns to the 0.2.23 extension behavior and replaces its custom base instructions with a DiCode-specific prompt adapted from OpenAI's Recommended Starter Prompt. It guides codebase exploration, tool selection, implementation, verification, and concise reporting. Approval behavior remains controlled by the app-server permission mode.

Version 0.2.26 registers Codex's dedicated `apply_patch` tool for DiCode model IDs through a generated model catalog. Without this metadata, Codex treats unknown IDs as fallback models and never offers the tool, regardless of prompt wording. The DiCode Responses gateway must support freeform custom tools for this to produce native file change events.

Version 0.2.27 checks the generated catalog against Codex CLI 0.164.0 using a local Responses probe. The CLI sends both `exec_command` and the custom `apply_patch` tool with automatic tool choice. A simulated gateway `apply_patch` custom tool call made that CLI create a file and emit `fileChange` start/completion events. The internal model and gateway still determine which call comes back in production. DiCode's instructions now explicitly direct text file creation, updates, and deletion through the standalone patch tool. The output channel records item types, command action types, and file change counts without command text, so an internal run can distinguish shell edits from native patch calls. The sidebar splits multiple `commandActions` into separate rows, shows thinking between active tools and the final reply, and pauses shimmer when hidden.

Version 0.2.28 uses the instruction template bundled with the installed Codex CLI instead of the former DiCode workflow prompt. The generated model catalog still registers `apply_patch` for DiCode model IDs, while `developer_instructions` adds only the DiCode identity. Exact model IDs use their matching bundled template; unknown IDs use the bundled model with the lowest priority number. Resumed threads receive the resolved native base instructions so old saved custom instructions are replaced. The DiCode Codex output channel logs the source model slug, SHA-256 digest, and template length for diagnosis.

Version 0.2.29 adds a short `apply_patch` tool description prefix for DiCode model IDs. It shows the exact Add File header and leading `+` required for each new line, and identifies `apply_patch` as the available edit tool instead of the unsupported `write` name. The CLI's native base instructions and the separate DiCode identity message stay unchanged. A gateway that ignores custom tool grammar still depends on the model following this example.

Version 0.2.30 changes Windows DiCode models to omit the dedicated freeform `apply_patch` tool and use `exec_command` to invoke `codex.exe --codex-run-as-apply-patch` through PowerShell 7.3+ in Standard argument mode. The Windows instructions show the required here-string and patch line prefixes. Codex's bundled base instructions remain unchanged. The extension puts both the verified portable `pwsh.exe` and its installed `codex.exe` on the CLI child process PATH. Shell edits may not emit native `fileChange` items; the sidebar can still show changes from the turn diff. This path is not used when PowerShell 7.3+ is unavailable.

Version 0.2.31 resolves `codex.exe` as an application and calls its absolute path, avoiding `.cmd` and `.bat` wrappers that can corrupt a multiline patch argument and produce a misleading missing `*** End Patch` error. The Windows patch instructions are written in Chinese for the internal model, while command names and patch syntax remain literal.

Version 0.2.32 renders live reasoning as a shimmering `思考中` line, lets each new command or edit replace the current activity heading, and folds prior activities under it. The next visible assistant text closes the activity run into a collapsed summary. Commands use only run labels; PowerShell calls to `codex.exe --codex-run-as-apply-patch` appear as file edits with filenames and line counts. Expanding a file row shows its diff in the conversation, and clicking its filename opens the VS Code diff editor once the diff arrives.

Version 0.2.5 keeps the same thread for follow-up questions after completion or interruption. The host state now includes the latest turn status, so the sidebar removes a stale working indicator after cancellation, interruption, or an error even if its terminal event arrives late. Null command output from app-server no longer breaks history persistence and the stop state. The conversation follows streaming output until the user scrolls up. The pinned prompt tracks the user turn at the top of the current viewport, and a floating control jumps to the bottom. The sidebar first renders the latest 30 turns and loads older turns in batches; at most 100 turns are kept in the persisted snapshot, subject to the 2 MB storage budget.

The composer has three Codex-native permission modes. 请求授权 uses `read-only` with `on-request`, 自动授权 uses `workspace-write` with `on-request`, and 完全访问 uses `danger-full-access` with `never`. The first mode is the default. The selected mode applies to the next turn, including when continuing an existing thread. Full access requires a modal confirmation and is reset when the extension or workspace changes. After the first completed turn, the extension asks the existing DiCode Responses bridge to generate a short title; this request has no tools and does not enter the conversation. Previously saved titles copied from the first prompt are updated when their thread is loaded.

On Windows, DiCode asks Codex to prefer the native MXC sandbox when the device supports it. Version 0.2.14 also selects Codex's `unelevated` legacy sandbox as the fallback when MXC is unavailable. Without a Windows sandbox backend, Codex 0.164 asks for approval even for ordinary read commands in a restricted permission mode. The `unelevated` fallback uses Codex's own restricted token and workspace access rules; it has weaker network isolation than MXC or the administrator-provisioned `elevated` backend. Organizations that have provisioned `elevated` can select it with `dicodeCodex.windowsSandboxFallback`. Organizational Windows policy may still prevent either fallback from starting. Approval cards show the reason and working directory supplied by Codex. Dismissing the full-access confirmation keeps the previous mode without reporting an extension error.

Version 0.2.6 adds ordinary Agent planning guidance: use the built-in `update_plan` tool for substantive multi-step work, update statuses as work progresses, and skip plans for simple tasks. Actual plan events still depend on the selected model and gateway tool-call support.

Version 0.2.7 keeps the correct user message pinned after jumping to it. When Codex requests user input, the sidebar shows its choices and a custom answer field above the composer, sends the answer through the app-server request, and continues the same turn. The card clears when the request resolves or the turn stops.

Version 0.2.8 enables `request_user_input` in ordinary Agent mode and the built-in `update_plan` tool when launching Codex. These flags apply only to the plugin's CLI process; users do not need to edit `config.toml` or the Codex binary. The selected model and gateway must still support function calls for the agent to invoke these tools.

Version 0.2.9 gives user-input requests an explicit custom-answer choice and a separate optional note for selected options. It also guides the agent to use structured questions when a consequential choice is needed. A simple question about whether a capability exists, or a request for freeform text, does not by itself require a structured selection. If an agent claims `update_plan` is unavailable, confirm that version 0.2.8 or later is installed and the VS Code window has been reloaded; model text alone does not establish what tools were present in the gateway request.

Version 0.2.10 uses a consistent circular radio control for question choices. Pointer selection no longer leaves the browser's native square focus indicator; keyboard focus remains visible on the option card.

On Windows x64/ARM64, the extension automatically downloads a verified portable PowerShell 7 package from the portal and prepends its directory to the Codex CLI child process PATH. The original Codex CLI discovers `pwsh.exe` through PATH. The extension probes the executable before starting the agent. This does not alter the user's system PATH or install PowerShell globally. The portal assets must be deployed before installing this VSIX. See `../../deploy/powershell-assets.md`.

This MVP supports login, model selection, a single persisted thread, streaming replies, command/file approvals, stopping a turn, and a new thread. It requires an open workspace. The old Roo-based extension is not part of this package.
