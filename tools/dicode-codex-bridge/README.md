# DiCode Codex bridge

Standalone Responses endpoint for the unmodified Codex CLI. Set `MODEL_ACCESS_URL` to the internal model-access service's `/ai-gateway/api/v1/models` URL, `GATEWAY_RESPONSES_URL` to the exact upstream `/v1/responses` endpoint, `TOKEN_EXCHANGE_URL` to chat-rag's `newTokenAuth.endpoint`, and `TOKEN_EXCHANGE_OPEN_TOKEN` to the same `NEW-OPEN-TOKEN` credential from a Secret. `REDIS_ADDR` defaults to `redis:6379`. The bridge validates the user's DiCode bearer token and selected model through model-access on every request, reads the verified JWT's email, reuses chat-rag's `chat_rag:new_token_auth` Redis hash, and on a cache miss exchanges the email for a key. It then sets `originator: codex_cli_rs`, forwards or generates `session-id` and `thread-id`, and streams the original Responses body and events without translation.

`GET /health` is unauthenticated. `POST /codex/v1/responses` requires a DiCode bearer token. It does not hold Codex sessions or run Codex itself; the VS Code extension starts `codex app-server` on the user's extension host.

Request diagnostics are always on. Each forwarded Responses request logs its session/thread/request IDs, model, stream and tool settings, input item roles and types, tool names, and the byte length and SHA-256 digest of developer/system messages. `codex_prompt` marks a developer message beginning with Codex's native opening; `dicode_identity` marks a message containing the DiCode identity. The extension's DiCode Codex output channel logs the selected bundled template digest. The digests may differ because Codex adds runtime guidance before sending a request. The diagnostic omits bearer tokens, user text, tool arguments, and full instruction text.

The bridge also logs every upstream HTTP status as `gateway_response`, HTTP error details as `gateway_error`, and `error`, `response.failed`, and `response.incomplete` SSE events as `gateway_error`. `gateway_output_item` records an actual output item type and tool name, while the request's `tools` list only shows tools offered to the model. `gateway_completed` records a completed response; `gateway_stream_end` records the byte count, elapsed time, last SSE event, and read result. `client_stream_error` identifies a downstream write failure. Event diagnostics omit tool arguments and response content. Error text is capped at 1 KiB per entry. The response status, headers, and stream bytes are forwarded unchanged. In the existing deployment, Promtail collects container stdout/stderr and Grafana's Loki data source can query `{app="dicode-codex-bridge"}`.

For latency diagnosis, filter bridge logs by `bridge_timing:` and group lines with the same `trace` value. The bridge forwards that value as `X-Request-Id` to the gateway, generating one if the caller did not provide it. `request_parse` covers reading and parsing the incoming body; `model_access` is the per-request model permission call; `token_auth` includes Redis cache read, optional key exchange, and cache write, with their own times and a `cache` hit/miss/error field. `gateway_headers` measures the upstream request through receipt of response headers. `first_byte` measures the wait from those headers to the first response bytes. `gateway_stream_end` includes total request time plus cumulative and maximum downstream write/flush times. Durations are in whole milliseconds, so a quick stage may read `0`. These are bridge-side timings; they do not measure APISIX-to-client delivery or local Codex processing. The VS Code extension's **DiCode Codex** output channel emits `[Codex timing]` markers for send, local client readiness, turn start, first item, and completion. A turn may contain multiple gateway requests and tool calls, so its total time is not directly comparable with one bridge request.

Build: `docker build -t dicode-codex-bridge:dev tools/dicode-codex-bridge` from the repository root.
